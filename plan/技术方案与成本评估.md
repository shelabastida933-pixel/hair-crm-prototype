## 一、需求还原

### 1.1 角色与权限（五层）

| 角色 | 能做什么 | 数据范围 |
|---|---|---|
| **客户** | 微信授权登录、自助预约、（授权时）选择技师 | 只能看自己的预约 |
| **员工（技师）** | 设置自己的工作时间、看自己的排班与预约 | 只能看自己 |
| **店长 / 店铺管理员** | 设店铺服务能力、管员工、代客预约、看本店数据 | 本店全部 |
| **总部运营** | 多店横向对比、全量运营数据 | 全部店铺 |
| **平台超管** | 开通/停用店铺、计费与配额 | 全部 |

### 1.2 核心业务规则（本次需求的关键约束）

```
① 预约最小粒度 = 30 分钟
② 可约时段 = 店铺营业 ∩ 员工在岗 ∩ 容量未满
③ 客户可指定员工，但受店铺开关控制，**默认关闭**
④ 预约必须校验店铺服务能力，防止冲突/超卖
⑤ 员工同一时间只能入职一个店铺（强约束）
⑥ 店长可代客户预约
```

### 1.3 最容易做错的三处（提前指出）

**（1）容量不能只按床位算**

养发馆 3 张床但只有 2 个技师在岗时，可约数 = **2**，不是 3。

```
剩余容量 = min(该时段在岗员工数, 空闲床位数) − 已占用数
```

只算床位 → 超卖，客户到店没人做。

**（2）「指定员工」默认关闭后，预约单会悬空**

客户约了 15:00 但没指定人 → 这条预约归谁？必须有个分配动作，否则员工端看到的是"有人要来，但不知道谁做"。

→ 建议：**默认由店长在后台分配**（客户无感，店长可改），并留"自动分配"作为可选策略。

**（3）30 分钟粒度 + 跨时段服务**

一次护理 60-90 分钟，但约的是 30 分钟格子。那么：
- 约 15:00 做 90 分钟 → 占用 15:00/15:30/16:00 三个格子
- **必须按"服务项目时长"锁多个格子**，否则 15:30 会被人重复预约

→ 数据模型里 `slot` 必须支持「一个预约锁连续 N 个格子」。

## 二、技术架构方案

### 2.1 三套可选架构（含成本）

| | **方案 A：微信小程序 + 云开发 CloudBase** | **方案 B：小程序 + 自建后端** | **方案 C：纯 SaaS 平台（多租户 Web + 小程序）** |
|---|---|---|---|
| 前端 | 小程序（客户/员工/店长合一，按角色渲染） | 小程序 + Web 管理后台 | 小程序 + Web 三端（总部/店长/员工） |
| 后端 | CloudBase 云函数 + 云数据库 | 自建（服务器 + MySQL/PG） | 自建多租户 |
| 开发量 | **最小** | 中 | **最大** |
| 月成本 | **¥19.9 ~ ¥199 起** | ¥100~300（轻量服务器） | ¥300+ |
| 上线速度 | **最快** | 中 | 最慢 |
| 适合 | 1~50 家店，快速验证 | 有技术团队、要定制 | 50 家店以上、要卖 SaaS |

**推荐方案 A**，理由见 2.2。

### 2.2 为什么推荐 CloudBase

| 理由 | 说明 |
|---|---|
| **微信生态原生打通** | 小程序免鉴权调云函数、直接拿 openid，省掉整套登录鉴权开发 |
| **手机号组件配合最顺** | `getPhoneNumber` 拿到的 code 可在云函数直接换取，无需自建服务端 |
| **免运维** | 无服务器、无数据库运维、自动扩容 |
| **按量起量** | 免费额度可用，起来再升级套餐 |
| **多租户可行** | 用 `tenantId / shopId` 做数据隔离 + 安全规则，云开发支持 |

**这个方案的代价（必须知道）：**
- 数据在腾讯云，迁出成本较高（供应商锁定）
- 复杂报表/大数据分析能力弱于自建 PG（总部横向对比要用预聚合表）
- 云函数的冷启动对首屏有影响（可用预留实例缓解，另计费）

## 三、数据模型（核心表）

```sql
-- 店铺
shops {
  _id, tenantId, name, phone, address,
  bedCount            -- 床位数（服务能力）
  businessHours       -- [{weekday, open, close}]
  allowCustomerPickStaff  -- ★ 客户可选员工？默认 false
  status, createdAt
}

-- 员工（关键约束：同一时间只能属于一个店铺）
staff {
  _id, shopId, openid, name, phone, avatar,
  role               -- 'staff' | 'manager'
  skills             -- ['白发转黑', '头皮护理']  能做的项目
  status             -- 'active' | 'resigned'
  joinedAt, leftAt
}
-- 唯一索引：openid + status='active' 只能有一条
-- ★ 这是"同一时间只能入职一个店铺"的硬保障，在数据库层约束，不靠前端

-- 员工工作时间（可设多段，最小 30 分钟）
schedules {
  _id, staffId, shopId, weekday,
  segments: [{ start: '09:00', end: '12:00' },
             { start: '13:30', end: '18:00' }]
  effectiveFrom, effectiveTo    -- 支持临时调班
}

-- 服务项目
services {
  _id, shopId, name, durationMin,   -- ★ 时长决定锁几个 30min 格子
  price, skillRequired
}

-- 预约（核心）
bookings {
  _id, shopId, customerOpenid, customerPhone,
  serviceId, durationMin,
  staffId          -- 可为 null（未分配）
  assignMode       -- 'customer_pick' | 'shop_assign' | 'auto'
  startTime        -- 30 分钟对齐
  slotKeys         -- ['2026-10-20T15:00', '2026-10-20T15:30', ...] ★ 锁多格
  status           -- 'pending' | 'confirmed' | 'arrived' | 'done' | 'cancelled' | 'no_show'
  createdAt
}
-- 唯一索引：staffId + slotKey（员工维度防冲突）
-- 唯一索引：shopId + slotKey + 序号（店铺容量维度防超卖）

-- 店铺时段容量（预计算，避免每次实时算）
shop_slot_capacity {
  shopId, date, slotKey,
  onDutyStaff,      -- 该格在岗员工数
  bedCount,
  capacity,         -- min(onDutyStaff, bedCount)
  booked,           -- 已约数
  remaining         -- capacity - booked
}
```

### 3.2 客户侧三张表（用户名单 / 预约 / 消费）

**这三张表是客户数据闭环，缺一条都算不出客户价值。**

```sql
-- ① 用户名单：客户是谁（全店/全公司共享的客户池）
customers {
  _id,
  unionid,            -- ★ 微信 unionid，跨店识别同一个人（关键）
  openidByApp,        -- 各小程序的 openid 映射
  phone,              -- 授权手机号（¥0.03/次换来的）
  name, nickname, avatar,
  firstShopId,        -- 首次来自哪家店（归因）
  source,             -- 'wechat_auth' | 'shop_created'（店长代建）
  tags: [],           -- 手工标签：['高价值','敏感头皮']
  createdAt, lastActiveAt
}
-- 唯一索引：unionid（同一微信只能有一条）
-- 唯一索引：phone（一个手机号一个客户）

-- ② 用户预约：他要来几次（时间维度）
bookings {            -- 见 3.1，此处只标注与客户的关系
  ...,
  customerId,         -- ★ 关联 customers，不是直接存 openid
  source,             -- 'customer'（自助）| 'shop'（店长代约）
}

-- ③ 用户消费：他花了多少钱（金额维度）★ 新增
orders {
  _id, shopId, customerId,
  bookingId,          -- 可为空（到店直接消费）
  staffId,            -- 服务技师（算产能用）
  items: [{ serviceId, name, price, qty }],
  amount,             -- 实收金额
  discount,           -- 优惠
  payMethod,          -- 'wechat' | 'cash' | 'card' | 'package'
  packageId,          -- 若用疗程卡核销
  status,             -- 'paid' | 'refunded' | 'partial_refund'
  paidAt, operatorId  -- 谁收的钱（店长/员工）
}
-- 索引：customerId + paidAt（查客户消费史）
-- 索引：shopId + paidAt（查店铺营收）
-- 索引：staffId + paidAt（算技师产能）

-- ④ 疗程卡 / 储值（养发馆必有的业态，否则核销没法算）
packages {
  _id, shopId, customerId,
  name,               -- '白发转黑 12次卡'
  totalTimes, usedTimes,
  totalAmount,        -- 卡金额
  status,             -- 'active' | 'used_up' | 'expired' | 'refunded'
  purchasedAt, expireAt
}
```

### 3.3 客户档案（聚合视图，不是新表）

**这是「用户名单」页面真正要展示的东西** —— 由上面三张表实时聚合：

```js
customerProfile = {
  // 身份
  name, phone, tags[], firstShopId,
  // ★ 预约维度
  bookingCount,           -- 总预约次数
  lastBookingAt,          -- 上次到店
  noShowCount,            -- 爽约次数
  // ★ 消费维度（钱）
  totalSpent,             -- 累计消费 ★ 客户 LTV
  lastOrderAt,            -- 上次消费
  avgOrderAmount,         -- 客单价
  orderCount,             -- 消费次数
  // ★ 卡状态
  activePackages: [{ name, remaining }],
  // ★ 运营标签（算出来的，不是手工打的）
  lifecycle: 'new' | 'active' | 'at_risk' | 'sleeping' | 'lost',
  riskReason: '60天未到店'    -- at_risk 的原因
}
```

**生命周期判定规则（建议）：**

| 状态 | 判定 | 运营动作 |
|---|---|---|
| 新客 | 消费次数 = 0 或 = 1 且 < 30 天 | 推首单/体验 |
| 活跃 | 30 天内有消费 | 维持，推加钟/升级 |
| **预警** | 30-60 天无消费，且卡内还有次数 | **重点挽回**（卡还没用完就走了） |
| 沉睡 | 60-90 天无消费 | 唤醒活动 |
| 流失 | > 90 天无消费**且卡已用完** | 低价召回 |

> ⚠️ 「预警」这条最值钱：**客户卡里还有钱但不来了** —— 这是养发馆最大的漏损，也是这套系统相对 Excel 的核心价值。

**为什么要有 `shop_slot_capacity` 这张预计算表：**
每次预约都实时算"这天这个时段有几个员工在岗"太慢（要遍历所有员工的排班）。
改成**每天凌晨预生成未来 30 天的容量表**，预约时只做一次 `remaining--` 的原子操作，又快又防并发。

## 四、核心算法

### 4.1 可约时段计算

```js
// 输入：shopId, date, serviceId(可选), staffId(可选)
// 输出：[{ slotKey, time, remaining, staffList }]

1. 取店铺营业时间 → 生成该日的 30min 格子
2. 过滤已过去的时间（now + 提前预约门槛）
3. 对每个格子查 shop_slot_capacity：
     capacity = min(onDutyStaff, bedCount)
     remaining > 0 ? 可约 : 不可约
4. 若指定了 service，按 durationMin 检查**连续 N 格**是否都有余量
5. 若客户指定了员工：
     该员工此时段在岗？+ 该员工 skill 匹配？+ 该员工此时段无预约？
     三者全满足才显示可约
```

### 4.2 防并发超卖（关键）

高并发下两个客户同时约最后一个位置 → 必须用**原子操作**：

```
云函数内用事务：
  doc = shop_slot_capacity.get(shopId+slotKey)
  if (doc.remaining <= 0) throw 已约满
  doc.remaining -= 1
  doc.booked += 1
  写入 booking
  （同一事务内完成，失败回滚）
```

**不要用「先查再写」**（`if remaining>0 then write`）—— 并发下必然超卖。

### 4.3 「指定员工」开关的实现

```
客户端渲染逻辑：
  if (shop.allowCustomerPickStaff === true)
      显示「选择技师」（列出在岗且会该项目的人）
  else
      隐藏技师选择，assignMode = 'shop_assign'

店长端：
  无论开关如何，都能在预约详情里「改派技师」
  （因为默认关闭的真实意图是"店里自己排"，不是"不许换人"）
```

### 5.2 工期换算

| 团队配置 | 总工期（含联调/测试/返工 30%） |
|---|---|
| 1 个全栈 | 约 **27-30 周**（6.5-7 个月） |
| 1 全栈 + 1 前端 | 约 **17-20 周**（4-5 个月） |
| 2 全栈 + 1 前端 + 1 设计 | 约 **11-13 周**（3 个月） |

> 工时含：需求确认、开发、联调、测试、修 bug。
> 不含：微信审核（1-7 天/次）、备案（7-20 天）、客户改需求。
>
> **⚠️ 加了消费+储值后总工期从 72 → 106 人日（+47%）。**
> 原因：消费记录不只是"记个金额"，它牵出疗程卡核销、退款、对账 ——
> 这是**收了钱就要负责**的模块，出错是财务事故，测试量远大于普通功能。

## 八、我的建议

### 8.1 不要一次做三期

```
现在最该做的：
  拿这份方案 + 演示原型 → 去跟客户谈
  让他确认：到底几家店、要哪些功能、预算多少
```

**理由：**"帮别人做的"项目，最大风险不是技术，是**需求在你和客户之间来回变**。
先拿到客户的真实预算和店数，再决定做 A/B/C 哪套。

### 8.2 如果是我做，我会这样切

| 阶段 | 交付 | 目的 | 周期 |
|---|---|---|---|
| **0** | 方案 + 可点击原型（本次交付） | 让客户看到长什么样、签字确认需求 | 已完成 |
| **1** | 单店 MVP 真能跑 | 拿 1 家店试，验证预约能不能用 | 3-4 周 |
| **2** | 多店 + 店长端 | 客户连锁店接进来 | 2-3 周 |
| **3** | 总部平台 | 有 10+ 家店才有价值 | 2-3 周 |

### 8.3 三个我必须提醒你的判断

**（1）总部平台是"有 10 家店"才需要的东西。**
4-5 家店的连锁做横向对比，用 Excel 都比做平台快。别为了"看起来完整"先做总部。

**（2）「指定员工默认关闭」这个设计，需要客户明确"那到底谁来做"。**
技术上我能实现，但业务上空着。建议方案里写成：**默认店长分配**，并把这个问题抛给客户确认。

**（3）这套系统的真正难点不在预约，在"员工排班的现实复杂度"。**
真实门店会有：临时调班、请假、加班、跨店支援、忙时加钟……
第一版建议只做"周模板 + 临时改某天"，别做完整的排班引擎 —— 那是无底洞。
